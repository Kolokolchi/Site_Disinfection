# Правила работы с Dis Cleaning

## Главное требование владельца

Текущий сайт — согласованная основа. Новый функционал добавляется точечно, с сохранением уже сделанной работы. Не переписывать сайт с нуля, не менять дизайн, структуру и существующее поведение за пределами задания. Это относится и к незакоммиченным изменениям, и к новым файлам в рабочей папке.

Перед изменениями прочитать этот файл и `docs/SITE_BASELINE.md`. Для выбора файлов использовать карту в `docs/ARCHITECTURE.md`. Правила действуют на весь репозиторий, включая HTML, CSS, JS, изображения и генераторы.

## Границы изменений

- Работать в существующем стеке: статический HTML, CSS, обычный JavaScript. Не переносить сайт на React, Next, Vue, CMS или новый сборщик ради отдельной функции.
- Сохранять внешний вид существующих блоков: композицию, порядок, размеры, отступы, цвета, шрифты, изображения, адаптивность, шапку, подвал и меню. Новые элементы оформлять в текущем стиле.
- Не удалять и не сокращать существующие страницы, тексты, услуги, отрасли, формы, переводы и мини-игру. Не переименовывать URL, классы, ID и ключи хранения без необходимости для явно заданного изменения.
- Не заменять логотип, фотографии, иконки или цены «для улучшения». Не возвращать удалённые прайс-страницу, команду, сертификаты и реквизиты из старых файлов или генераторов.
- Новая функция не является разрешением на редизайн, массовое форматирование, уборку старого кода, обновление всех зависимостей или переписывание соседних разделов.
- Явная просьба владельца изменить конкретную часть разрешает это изменение; отдельное повторное подтверждение не нужно. Остальная основа сохраняется. Если для задачи действительно необходим более широкий пересмотр, сначала обосновать зависимость и уточнить именно расширение задачи.

## Перед началом

1. Выполнить `git status --short`, прочитать затрагиваемые файлы и существующие тесты. Не считать HEAD более правильным, чем рабочая папка. Не откатывать чужие изменения, не выполнять очистку/сброс и не восстанавливать удалённые страницы автоматически.
2. Кратко обозначить, какую функцию добавляешь и какие компоненты она затронет. Выбрать минимальный набор файлов.
3. Для правок интерфейса снять актуальные скриншоты затрагиваемых страниц до изменения на мобильной и настольной ширине. Исторический эталон находится в `docs/baseline/2026-09-29/`; уже согласованные более поздние изменения тоже сохраняются.
4. При работе с генератором сначала изучить, что он перезаписывает. Существующий HTML — источник фактически принятого результата; генератор не получает приоритет только потому, что он существует.

## Во время работы

- Применять локальные патчи. Не заменять целиком страницу или таблицу стилей для небольшой задачи.
- Новые стили ограничивать классом компонента. Не менять глобальные `section`, `.wrap`, `.btn`, `h1`, `:root` и контрольные ширины ради одного блока. Если общая правка прямо требуется заданием, проверить все семейства страниц.
- Сохранять порядок подключения: `css/style.css` → `css/theme.css`; `js/main.js` → `js/interactions.js`. Учитывать импорты CSS, каскад и переопределения словарей переводов.
- Расширять текущую реализацию, не создавать второй обработчик формы, второй слайдер, второй переключатель языка или дублирующую загрузку игры.
- Сохранять работу внутренних относительных ссылок, открытие HTML с диска для статического интерфейса, RU/KZ, клавиатуру, Escape, возврат фокуса, reduced motion и мобильную панель контактов.
- `tools/build_catalog.py` перезаписывает все страницы услуг и объектов, `objects.html` и секцию объектов главной. Не запускать его ради одной локальной функции. Если генерация необходима, сохранить все актуальные ручные доработки в шаблонах/данных до запуска, затем проверить весь полученный diff. При точечной правке HTML также обновить соответствующий источник, если он существует, без обязательной массовой пересборки.
- `tools/sync_layout.py` применять только после намеренной правки общих блоков в `index.html`; он затрагивает все внутренние публичные страницы. Проверять относительные пути и отсутствие побочных замен.
- Остальные скрипты миграции/перестройки в `tools/` не являются обычной сборкой. Не запускать их для «обновления сайта». Подробности — в карте архитектуры.
- Не ослаблять тесты и не подменять эталон ради прохождения проверки. Не отправлять реальные заявки при тестировании: перехватывать WhatsApp и внешние интеграции.

## Перед завершением

1. Проверить собственный diff, включая созданные файлы; отделить его от исходных пользовательских изменений. Удалить только свои случайные правки вне задачи.
2. Выполнить `python tools/check_baseline.py`: это отчёт об отличиях от исторической основы, а не требование вернуть все файлы к старой версии. Сопоставить изменения с задачей и состоянием до начала; прежние согласованные доработки не откатывать.
3. После изменения публичного сайта выполнить `python tools/audit_public.py`. При общих CSS/JS, шаблонах, навигации или генерации выполнить `npm test` целиком; при локальном поведении — соответствующие тесты и ручную проверку затронутой страницы. При изменении только документации браузерные тесты повторять не требуется.
4. Для визуальных правок сравнить до/после при одинаковых условиях минимум на 390 и 1440 px; проверить 320 px на переполнение. Для общих стилей проверить главную, каталог, отрасль, объект и услугу. Скриншоты сами по себе не являются автоматическим тестом сходства.
5. Проверить, что новый функционал работает, а существующие блоки вне задания не изменились. Не выдавать наличие файлов/скриншотов за успешную проверку поведения.
6. В результате указать изменённую функцию, затронутые файлы, проведённые проверки и реальные ограничения. Найденные старые проблемы сообщать отдельно, не исправлять их расширением задачи без необходимости.

Нельзя перезаписывать исторический эталон автоматически. Новую версию эталона создавать отдельно при явном принятии владельцем новой основы; предыдущую сохранять. Проверочный скрипт не должен менять сайт.
